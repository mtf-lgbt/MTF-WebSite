## 前言

欢迎来到 MTF.LGBT 使用手册。MTF.LGBT 是一个面向跨性别群体的公益项目，希望为大家提供域名、邮箱、内容发布与交流等力所能及的服务。本手册汇总了目前常见功能的申请与使用方法，包括三级域名申请、邮箱注册、文章与 Subtitle 投稿、RSS / 邮箱订阅、翻译贡献、友情链接、Bug 提交、Pull Request 提交以及合作事宜等。

如果你是第一次来到这里，可以先按目录找到自己需要的部分；如果你已经使用过部分服务，也可以把本手册当作一份随时查阅的说明。由于项目由站长和志愿者维护，域名续费、邮箱等基础设施都依赖赞助和有限资源，因此请按需申请、合理使用。域名申请、文章投稿等内容通常需要审核，请耐心等待，避免重复提交。

手册内容会随着网站功能更新而调整。若手册与页面实际情况不一致，请以网站实际页面和 Issue 中的回复为准；尚在改造或未完成的功能，也会在对应章节中标注说明。遇到问题时，建议先阅读相关章节，若仍未解决，再到 GitHub Issue 中提问，并尽量附上截图、链接和复现步骤。

感谢每一位使用、投稿、翻译、反馈和赞助的朋友。希望这份手册能帮你更顺利地使用 MTF.LGBT，也欢迎更多人一起参与维护，让这里成为对跨性别者真正有用的空间。

## 文章和Subtitle投稿

点击[这里](https://forms.gle/b4BHnN71oqEskqYL9)填写您所投稿的内容。会经过审核后通知您是否通过。

对于投稿，你需要知道以下这些事情：  
你可以选择两种投稿方式，第一种就是将您的文章的markdown文件投稿到我这里，这种最简单也最直接，性能也最好。另外一种是将你的文章raw链接投稿到我这里，这种因为需要取用你的服务器或者网站，因此性能会变得很弱，但可以时刻保持更新。

### 文件投稿

一般情况下，你只需要在文章头部将你的大标题去掉并发给我即可，这是因为本网站文章的标题都位于数据库中。您并不需要太过于担心。因为如果没有去掉，我也会帮你删除掉。此外你还需要告诉我作者、创作日期、语言和你想要的标签信息。

### url形式投稿

这种投稿方式的初衷是为了那些还没有完成创作，或者是一直在持续创作的文章而设计。因为数据直接取自你的网站，你在修改时本网站的内容也会同步更改。但是我要说明一点的是，这个模式会让性能大幅下降，原因是访客在打开的时候还要加载你的网站，如果你的网站还因为gfw的原因无法访问时，访客如果没有vpn等工具将无法查看。因此对于已经完成创作不会更改的作品，我会要求你直接给予源文件，以保证访客的正常访问。

对于投稿的链接要求，需要看具体的储存架构。不是说将你的页面提交上即可，而是需要一个直接显示原始内容的链接。一般我们称作raw链接。打开看到的是文件本身最纯粹、未经处理的内容。如果是一个脚本，它就是可执行的代码；如果是一个文本，它就是纯文本，一般用于程序直接读取或下载。在这里，就是markdown的文本链接。

我不能保证你的raw链接一定在哪个地方，但是我会尽量覆盖可能的情况：

1. 你的文件在你的github仓库里

这种的最简单，直接打开https://raw.githubusercontent.com/{你的用户名}/{你的仓库名}/{你的仓库名称}/你的文章markdown文件目录和文件名.md

## 翻译
> 这一段比较重要，我会在README.md中也写明。

首先很感谢您为我们的项目提供翻译，我们的翻译系统结构分为两个部分：词条翻译和内容翻译。

词条翻译和内容翻译的区别：

| 项目 | 词条翻译 | 内容翻译 |
| --- | --- | --- |
| 描述 | 对于标题、按钮文字、链接文本等内容采用原生的i18n国际化模组进行翻译。基本不会进行修改 | 对于长文、活动、通知等不方便放入JSON档案的文字，会采用内容翻译。比如「关于我们」页面。修改频率相较于词条翻译会多一些 |
| 特性 | 翻译内容严格一一对应，不过如果你发现一个文件塞了太多内容，你可以将一部分词条拆出来放在单独的文件里。（站长警告你别拆的太抽象别人看不懂） | 不同语言可以写完全不一样的文字，甚至可以添加区域性的活动通知。有点不像是单纯的翻译了，更像是区域设置。只不过这个「区域设定」会随着翻译设置的变化而变化，而不是平时我们见到的语言是一个设置项目，区域一个设置项目 |
| 位置 | ```./src/i18n``` | ```./src/routes``` |

### 注册

首先我们可以学习一下目前（2026-10-24）的目录结构：
```dash
src/i18n
├── i18n.js
├── supportLocales.js
├── ja
│   ├── blogs.js
│   ├── friends.js
│   ├── home.js
│   └── master.js
└── zh-cn
    ├── blogs.js
    ├── friends.js
    ├── home.js
    └── master.js
```
在这之中，```i18n.js```充当一个注册机，基础翻译工作在这里汇总。

首先需要在```i18n.js```顶部import一个根文件，作为你语言翻译的起点。一般情况下根文件位置应该创建在```src/i18n/<Language Code>/master.js```，具体写法可以参考已有的import。   
随后，你需要在message中加入你刚才import的名字，比如你如果写的是```import enus from './en-us/master.js'```，在message上就要写```enus```。

#### 按钮注册

要让语言在设置菜单中能够选择，你需要在```src/components/setting.vue```中将你的语言注册在前端的按钮中。

在这个文件中你找到```const langs``这一段，它大概长这样：
```js
const langs = [
    { code: 'zhcn', label: '简体中文' },
    { code: 'enuk', label: 'English UK' },
    { code: 'ja',   label: '日本語' }
]
```
其中code就是你的语言id，label是你的语言在按钮上显示的文字。

#### 变体机制

一个语言不总是一样的，这个我相信中文语言者和英语语言者深有体会。大陆和新加坡华人使用简体中文，港澳台三地使用繁体，就算是这样也会分粤语繁体和台湾繁体以及正体中文（正體中文）英语更是恐怖，加拿大、美国、英国乃至印度都有截然不同的English。为了区分这些地区，以及实现区域性的内容和变种语言或者文艺性语言，以及最重要的：适配浏览器语言设置，我们将使用变体机制。

<m3e-callout variant="primary">
    <m3e-icon slot="icon" name="info"></m3e-icon>
    <span slot="label">注意！</span>
    <p>如果不将你的语言加入到变体列表中，将该变体设置为浏览器默认语言的用户会无法自动使用你的语言，除非你的语言并非某个区域在事实上正在使用的一种语言。或者你百分之百确定浏览器不会被设置这样的语言。</p>
</m3e-callout>

##### 原理

现代浏览器可以给网页提供用户给浏览器设置的语言，一般的格式是[语言]+[地区]。比如这些：```zh-CN en-US ja```。变体机制会将其拆分成一个数组，比如大陆中文会拆成[zh][cn]。随后，机制会逐一比对，以美式英语和日本语举例，所有的可能如下图：
| No | 如果 | 结果 |
|---|---|---|
| 1 | 有en，有us |  使用enus |
| 2 | 有en，没有us | 使用en变体列表中的第一个变体，比如enuk |
| 3 | 没有en | 使用默认语言zhcn |
| 4 | 没有任何变体，比如ja | 直接使用ja |
| 5 | 没有变体，比如ja，但是浏览器传入的是ja-JP | 直接使用ja |

##### 注册变体

一般来说，**只有区域性语言会有影响用户体验的理由去注册**，文艺性语言大概不会有浏览器闲的蛋疼去传入一个[魔法师中文](https://translations.telegram.org/encha/)，自然也不会被用户自动选中，只能靠Setting页面手动切换。因此暂时也不会有什么影响用户体验的事情。但是在未来可能会出现对于未翻译的内容的默认变体设置，因此还是建议去注册一下为好。

具体注册步骤为：
- 打开supportLocales.js，你在里面会看到这个东西，相信只要有一点逻辑就能看懂里面的**层级结构**：
```js
const SUPPORT_LOCALES = {
    zh:[
        'cn'
    ],
    en: [
        'uk'
    ],
    ja:[]
}
```
- 在对应的语言中写入变体id，比如印度英语是en-IN，就在en:后面的方框内填入你的'in'。
- Ctrl+S OR Command+S保存

<m3e-callout variant="primary">
    <m3e-icon slot="icon" name="info"></m3e-icon>
    <span slot="label">注意！</span>
    <p>因为列表第一列属于标准语，在没有区域性翻译时会优先使用标准语。如果你的语言极具地方性，比如印度英语等，禁止放入上述json的第一列，否则在合并时会勒令整改或者拒绝合并</p>
    <p>如果你认为你的语言属于标准用语或者标准有争议，请在网站github仓库**提交Issue并由社区投票决定**。但一般不会这么麻烦，主要以调解和仲裁为主。</p>
</m3e-callout>

我知道可能有些人听着有些蒙，在这里做个省流：区域性语言（如 en-IN）必须注册，且只能放在第一列之后；文艺性语言（如魔法师中文）可以不注册，若注册同样只能放第一列之后 （2026-11-07）

### 词条翻译

#### 架构

没有什么好说的，照着其他语言的架构抄就可以。只有一个重点需要注意下：

这是根文件的基础架构
```js
const zhcn = {
    ···
}
export default zhcn;
```
你只需要保证「const」后面的那个单词以及「default」后面的那个单词是一致的，并且和```i18n.js```中相应import的名字一致就可以。

### 内容翻译

这一段比较简单，在```/src/routes/```中创建一个文件夹（如果还没有人翻译），在文件夹内创建你要翻译的页面的名字加```.md```——比如「关于我们」页面需要创建```about.md```。但是有一个特例，就是主页，或者一般程序语境下的「index」。你需要创建```home.md```而不是```index.md```。

另外，你在创建文件夹时文件夹名称应该是```src/i18n/i18n.js```中import语言根文件时的名字。

至于如何写，直接参考[vitepress的wiki](https://vitepress.dev/guide/getting-started)，因为相关插件就是把它当vitepress来处理的，即便这个项目是个正经的Vue项目。

### 命名规范

1. 对于routes的文件夹名称、各个注册位置写的语言id，一律强制性的使用诸如 zhcn、zhtw、enus、enuk 这类格式。
2. ```src/i18n/```下的文件夹名和 import 路径可以随意，一般在习惯上来说建议使用zh-cn、en-uk、ja，但 master.js 里 const {变量名} = {...} 和 export default {变量名} 的变量名、以及 i18n.js 里 import {变量名} from ... 的变量名、messages 的 key、routes/ 下的文件夹名，这五处必须完全一致，且强制使用 zhcn / enuk / ja 这种无连字符格式。
